# 06 · 质量与验收规则（DOD / 门禁 / 测试 / 修复 / Dogfood）

> 立规日期：2026-06-13。本文是**可重复执行的质量管控规则**：每一轮开发/评审都对照本文走查。它把"完成"从感觉变成可核对的清单，避免半成品流转。
>
> 适用范围随阶段递进——当前为**文档先行阶段**，多数代码类门禁尚无被测对象；本文同时预置二期（规则数据）、三期（CLI/MCP 代码）的门禁，让后续开发直接继承，不必重新发明。

---

## 0. 阶段模型与"现在算不算 N/A"

| 阶段 | 工件 | 已就绪门禁 | 暂不适用（无被测对象） |
|---|---|---|---|
| P0 文档先行（**当前**） | `README` + `docs/*` + `schemas/*.json` + 治理文档 | 文档一致性、schema 契约测试、DOD-P0 | 源码扫描、E2E、性能、漏洞审计 |
| P1 规则数据 | `flow.yaml` + `rules/*.yaml` + 种子规则 | schema 校验、来源可回链、图 linter、规则 lint | 同上（仍无运行时） |
| P2 代码骨架 | CLI 内核 + MCP 适配 | 全部 6 类门禁正式生效 | — |

> **诚实原则**：暂不适用的门禁标 `N/A（待 Px）`，**不允许**用"无代码"伪装成"全绿通过"。验收报告必须显式列出 N/A 项及其解锁阶段。

## 1. DOD（完成定义）—— 对抗审查准入

任何任务/功能/版本要"完成"，必须逐项满足对应阶段 DOD，**未满足即不得流转**。

### DOD-P0（文档先行）
- [ ] 每个结论可回链官方/准官方来源（`official_url` + `source_quote` + `last_verified`）。
- [ ] 跨文档无矛盾：同一事实只有一个权威源，其余为引用（边界以 `docs/02` 为准）。
- [ ] 计数/枚举类陈述与实际条目一致（如"N 个决定"= 表中行数）。
- [ ] 边界口径不越界：不出现"全网没人做""保证过审""已合规""一键上线""可直接提交"。
- [ ] 新增/改动经**独立审查**（作者与审查不同上下文），高风险经对抗式红队。

### DOD-P1（规则数据）
- [ ] `rules/*.yaml`、`flow.yaml` 通过 `schemas/*.json` 校验（CI 强制）。
- [ ] 每条默认规则必带来源；低置信进 `draft`，不进默认集。
- [ ] 涉及官方后台提交/认证/备案/类目/隐私/域名/发布的规则 `manual_required: true`。
- [ ] 预检规则声明 `scanner`，动态命中用 `manual_only` + `dynamic_note`，不以 LLM 猜测冒充。
- [ ] `flow.yaml` 通过**图 linter**：指向存在、无环、唯一入口、唯一终点（`release` 为唯一 `next: null`）。

### DOD-P2（代码）
- [ ] 单元/接口/集成/冒烟测试通过；关键路径有 E2E。
- [ ] 预检默认 local-only；脱敏与忽略清单生效（见 `SECURITY.md`）。
- [ ] CLI 零运行时依赖优先；新增依赖须说明理由并过安全审计。
- [ ] 性能基线达标（见 §4 性能门禁）。

## 2. 代码质量门禁（按阶段解锁）

| 维度 | 工具/方法 | 阈值（建议） | 阶段 |
|---|---|---|---|
| 数据模型规范 | `schemas/*.json` 校验 | 0 校验错误 | P0/P1 |
| 文档一致性 | 链接体检 + 计数/枚举核对 | 0 死链、0 计数错位 | P0 |
| 编码规范 | ESLint + Prettier（二期定 config） | 0 error | P2 |
| 代码复杂度 | 圈复杂度（如 ≤10/函数） | 超阈需说明 | P2 |
| 静态安全扫描 | `npm audit` / CodeQL / semgrep | 0 high/critical | P2 |
| 漏洞与隐私审计 | 人工 + 规则：不回显密钥/PII，无远程上传默认开 | 见 `SECURITY.md` | P2 |
| 技术债登记 | `// TODO(债务编号)` + 债务台账 | 不堆积、有计划 | P1/P2 |

> P0/P1 的"代码"就是 schema 与规则数据：把门禁前移到数据层，是"规则即数据"架构应得的红利。

## 3. 缺陷修复清单与分级策略

每轮把缺陷登记为修复清单，**统一分级处理**，修复后必须**回归验证**：

| 处理方式 | 触发条件 | 时限 | 回归要求 |
|---|---|---|---|
| **热修复** | 阻断交付准入（DOD 不过）、对外口径越界、schema 与示例自相矛盾、密钥泄露风险 | 本轮内 | 必须复跑相关门禁，留证据 |
| **延期修复** | 不阻断当前阶段、但二期前必须解决（如缺 issue 模板、缺 CI） | 标注解锁阶段 | 进入对应阶段时复检 |
| **不予修复** | 设计取舍/误报/超范围（如多端扩张诉求） | 永久 | 记录理由，避免反复提起 |

> 修复清单与回归证据每轮追加到本文末「修复台账」或单独的 `docs/fixlog/` 中（二期）。

## 4. 测试策略（全链路，按阶段落地）

测试金字塔在本项目的具体含义：

| 层级 | 测什么 | 现状 |
|---|---|---|
| **契约测试**（现存唯一可跑） | 示例规则/flow 是否符合 `schemas/*.json`，含反例（越界规则必须被拒） | ✅ 已通过（P0） |
| 单元测试 | 扫描器从源码提取域名/隐私 API/配置的纯函数 | ⏳ P2 |
| 接口测试 | CLI 子命令入参→输出契约（`check` / `guide` 的 JSON 报告 schema） | ⏳ P2 |
| 集成测试 | 规则库 + 扫描器 + 渲染器串起来，喂真实小程序源码 | ⏳ P2 |
| 冒烟测试 | `check ./fixture` 与 `guide` 在样例项目上不崩、出非空报告 | ⏳ P2 |
| **E2E** | 从"用户答问卷/给源码"到"拿到个性化上线清单"全流程 | ⏳ P2 |
| 性能 | 预检在中型小程序（数千文件）上耗时/内存基线（如 < 5s、不 OOM） | ⏳ P2 |

> **E2E 锚点**：用 §0 Go/No-Go 的"3 个真实/模拟小程序跑出有价值报告"作为 P2 的 E2E 验收集。
> **测试夹具**：二期建 `fixtures/`（脱敏样例小程序）作为集成/E2E/性能的共享输入。

## 5. Dogfood 协议（交互与体验）

以**真实目标用户**视角验证，而非作者视角：

- **导航 Dogfood**（来自 `docs/04` Go/No-Go）：找 ≥5 个零基础/个体开发者读 `guide` 输出，≥3 人能**自述下一步该做什么**，否则导航文案不过关。
- **文档 Dogfood**（P0 现在可做）：以"刚用 AI 写完代码、零上线经验"的人读 `README`，记录每一处"看不懂/会误操作/找不到下一步"的摩擦点，回灌为改进项。
- **Agent Dogfood**（P2）：让 Claude Code / Codex 实际调用 CLI/MCP，检查衔接是否顺、输出是否可被 Agent 正确解释。

## 6. 分维度优化（每阶段复盘四问）

每轮结束按四个维度各回答一句"本阶段最大短板 + 一个可落地动作"：

- **质量**：哪条结论来源最弱/最可能腐烂？→ 加来源或降级 `draft`。
- **效率**：哪步靠人工重复？→ 能否脚本化（如链接体检、计数核对、schema 校验）。
- **稳定性**：哪条规则/分支最易随政策失效？→ 加 `last_verified` 监控与告警。
- **可维护性**：哪处是多事实源/重复？→ 收敛到单一权威源 + 引用。
