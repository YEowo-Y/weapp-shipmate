# 社区 Agent 前端调研、项目评审与差异化设计

调研日期：2026-10-22。适用项目：上线船友（小程序上线导航、代码预检、拒因定位与模型对话）。实施计划见 [community-agent-design-plan-20261022.md](community-agent-design-plan-20261022.md)。本轮实际阅读论坛、社交帖子、开源项目讨论及官方文档；未把社区提案写成已上线功能，也未声称检查过这些项目的全部源码或最新客户端。

## 对当前功能的评审

| 用户任务 | 现有能力 | 本轮决定 / 边界 |
| --- | --- | --- |
| 读懂拒因并决定先做什么 | 真实本地规则匹配、校验、步骤、人工确认标记、官方原文与链接 | 落地处理重点筛选，直接使用校验字段，浏览器与正式桌面共用。 |
| 将结果交给别人或稍后继续 | 完整复制、下载 Markdown、加入当前会话 | 继续输出完整结果，明确筛选只影响视图，避免遗漏被隐藏项。 |
| 判断依据可信程度 | 收录链接、原文、仓库核验日期 | 明示“未收录官方链接”及“未实时核验”；无链接不等于规则错误，有链接不等于本次已验证。 |
| 查询失败或无结果 | 错误重试、保留输入、停止查询 | 筛选零项与查询未命中分别处理；筛选零项无需重新查询，按钮恢复全部。 |
| 使用真实模型与上下文 | 连接、选择、流式、停止、会话存储 | 不改本轮模型/认证协议。报告进入会话不应被解释为具备完整的显式附件授权设计。 |
| 查看上线清单 | 浏览器结构化 guide 与桌面 CLI Markdown 两条路径 | 尚未统一结果展示，不能声称改浏览器卡片就覆盖正式桌面清单。 |
| 执行有副作用工具 | 部分预览包含交互演示 | 通用模型工具运行、真实业务审批仍需服务端执行绑定；本轮不扩权，也不伪造操作完成。 |

## 已落地：拒因处理重点

从“长结果逐条阅读”改成“先按需要定位，再逐条看依据”。针对小程序上线的具体任务，同时保留确定性控件和原始规则细节。

| 控件 | 唯一数据依据 | 呈现约束 |
| --- | --- | --- |
| 全部 | 校验后的全部 items | 数量叫“匹配项”；同一规则可匹配不同拒因，不能误叫独立规则数。 |
| 需处理 | severity === blocker | 是规则库的严重级别，不证明该问题已在用户项目中实际发生。 |
| 需本人确认 | manual_required === true | 用户可快速找出后台配置或人工办理项；不自动勾选完成。 |
| 缺少官方来源 | official_url 为空 | 精确定义为未收录链接，提示用户自行核对；不自动生成引用。 |

- 分类允许重叠，不用环形图、完成率或加总到 100%。
- 直接隐藏已有条目和空分组，保留原文展开状态；不重新创建整份结果、不请求模型。
- 过滤按钮保留焦点，动态数量以 polite 状态播报；零项“查看全部”重置后将焦点移到可见的“全部”按钮。
- 关闭已完成结果后再开，保留处理重点；修改输入清除旧结果，新查询默认全部。
- 复制、下载、加入会话始终包含完整已校验结果；界面明确告知这个边界。
- 共用现有颜色、圆角和字体 token；数量等宽，窄窗口折行，触控目标至少 44px，保留键盘和高对比焦点，不新增旋转加载或筛选动画。

入口：工作台“处理审核拒因”或桌面更多菜单 → 粘贴反馈 / 填入标注的示例 → 查询本地规则 → 选择处理重点 → 展开原文核对 → 完整导出或加入会话。示例只填入输入，必须运行真实本地查询才能得到结果。

## 后续差异化设计（本轮未实现）

这些是围绕项目能力的设计建议，不宣称行业首创，也不伪装成可用入口。

### 1. 显式的“带着这份报告继续问”

目的：从代码预检或拒因结果进入模型解释，减少用户重新描述，同时避免静默上传本地内容。

设计：结果区选择“用于下一次提问”，发送前展示报告名、生成时间、来源项目、大小、目标模型/厂商及可移除的上下文项；预览实际内容，确认后才加入下一次模型请求。状态区分未选择、已选择未发送、发送中、已发送、失败可重试。错误或模型切换不丢用户草稿；取消和迟到响应不得重新发送。模型不支持该输入时给出明确替代入口，不伪装附件能力。

需要先补齐报告身份/版本、可复核内容、大小限制以及传输测试；现有“加入会话”只是结果保存能力，不能等同这个发送授权流程。建议优先级：下一阶段。

### 2. 有依据的复查差异

目的：回答“修改之后，哪几项真的变化了”，而非用用户打勾伪造完成率。

设计：对同一项目、同一检查范围的两次真实预检，按稳定规则 ID 比较新增、仍存在、未再检测到与无法比较；显示扫描时间、规则库版本和检测范围。条件改变、扫描不完整或规则升级时显式说明，不能将缺失项自动叫“已合规”。原始两份报告始终可展开和导出。

需要持久化运行标识、项目/范围/规则版本，并验证扫描失败与版本变化的比较语义。目前 stages.js 中的 done/cur/todo 是示例状态，不得作为这个功能的数据源。建议优先级：报告版本机制完成后。

### 3. 人工办理交接清单

目的：将自动检测与确需本人进入官方后台的动作分开，方便开发者与业务负责人交接。

设计：复用本轮“需本人确认”，在未来结构化动作模型中区分配置、材料、后台操作和确认依据，附官方入口与待确认事项，输出可交接文件。只有用户明确确认时记录“用户确认”，与自动检测结果分列，撤销可追溯。

当前 requires 混合了操作、配置和材料，不具备稳定动作类型；本轮因此保留原步骤而不建立伪“材料齐全”控件。建议优先级：有真实交接场景与数据模型后。

## 视觉建议的工程取舍

沿用轻层级和较少边框，但过滤选中、输入与键盘焦点仍需清楚。没有机械执行“暗色字重减 40”“单字延迟 30ms”“取消 outline”等社交经验：系统字体不保证支持 360 字重，逐字延迟会拖长输出，删除焦点会损害键盘操作。当前切片无需新增动效库，状态变化即时完成。实际布局与可用性以 Windows WebView2 截图、键盘流程及单元/契约测试为证，不用主观分数代替验收。
