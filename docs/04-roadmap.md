1. **开源包装** —— README（中英）/ LICENSE（MIT）/ CONTRIBUTING / SECURITY / GOVERNANCE / issue 模板 / 规则贡献指南。先让项目能被安全地讨论和贡献。
2. **`flow.yaml` + `rules/*.yaml` schema** —— 第一批数据文件，不是 CLI。先把**流程图骨架**（导航的阶段顺序/分支/前置）和**规则数据模型**一起定死（见 `03-decisions-and-architecture.md` 的「导航图模型」与「规则 schema 草图」）。配一个 schema 校验脚本，保证社区 PR 的规则结构合法、必带 `official_url`、`source_quote`、`last_verified`；`flow.yaml` 同样带来源与校验日期。
3. **种子规则** —— 手工灌入 30 条以内高质量规则，优先备案、服务类目、隐私、服务器域名、提审材料和常见拒审原因。
4. **CLI 内核** —— `weapp-shipmate check ./app`（代码感知预检：本地扫源码 → 命中规则 → 出个性化上线清单）。零运行时依赖优先。
5. **导航决策树渲染** —— `weapp-shipmate guide`（把同一份规则库当流程导航渲染）。
6. **MCP 适配层** —— 包一层 MCP server，把 CLI 能力暴露给 Claude Code / Codex。MCP 是 v0.2，不是 v0 首发阻塞项。

### 建仓前的质量门
- 先跑一轮**对抗式红队**审 `rules/*.yaml` 的 schema（符合"先讨论再动手"的习惯）。
- 建仓前再做一次 `npm view weapp-shipmate` 权威终检。
- 所有规则必须能回链官方或准官方来源；没有来源的规则只能进 `draft`，不能进默认规则集。
- 预检必须默认 local-only，且默认忽略密钥、证照和私有配置文件。

### v0 发布前 Go / No-Go 条件

- [ ] 1 周内整理出 20-30 条高质量种子规则。
- [ ] 用 3 个真实或模拟小程序跑出有价值的预检报告。
- [ ] 找 5 个目标用户读导航，至少 3 个能说清"我下一步要做什么"。
- [ ] 每条结论都能回链官方来源，不靠模型自由发挥。
- [ ] README、SECURITY、CONTRIBUTING、Issue 模板齐全。

如果做不到这些，先停在"文档导航 + 案例库"，不要急着做 CLI/MCP。

## ⚠️ 二期前值得先想清的待决问题

**冷启动：第一版种子规则由谁来灌？**

规则库的"保鲜"靠社区 PR，但冷启动时社区还不存在。建议：

> 第一版的**种子规则（备案 / 类目 / 隐私 三块）**，由我用调研到的官方文档**手工灌入**，让工具一上线就能用、再靠社区增量保鲜。

这三块是零基础用户最高频踩坑、且官方规则相对稳定可固化的部分，作为冷启动种子性价比最高。

## 风险登记（持续更新）

| 风险 | 缓解 |
|---|---|
| **规则腐烂**（微信政策每几月变） | 规则即数据 + 每条带 `last_verified` + 社区 PR 保鲜 |
| **"全流程"摊死** | 共用一份规则库脊柱；种子只做备案/类目/隐私三块 |
| **责任边界**（建议给错坑用户） | 全程官方链接 + 原文短摘录 + 校验日期；不做担保；输出只做待确认建议 |
| **源码 / 密钥泄露** | 预检默认 local-only；忽略密钥文件；报告做脱敏 |
| **合规文书越界** | 不代写正式合规文件；只做字段映射、待确认草稿和检查清单 |
| **多端扩张诱惑**（抖音/支付宝小程序） | 明确承诺小而美、只聚焦微信；`weapp-` 前缀即承诺 |
