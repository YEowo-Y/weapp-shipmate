## 1. DOD（完成定义）—— 对抗审查准入

任何任务/功能/版本要"完成"，必须逐项满足对应阶段 DOD，**未满足即不得流转**。

### DOD-P0（文档先行）
- [ ] 每个结论可回链官方/准官方来源（`official_url` + `source_quote` + `last_verified`）。
- [ ] 跨文档无矛盾：同一事实只有一个权威源，其余为引用（边界以 `docs/02` 为准）。
- [ ] 计数/枚举类陈述与实际条目一致（如"N 个决定"= 表中行数）。
- [ ] 边界口径不越界：不出现"全网没人做""保证过审""已合规""一键上线""可直接提交"。
- [ ] 新增/改动经**独立审查**（作者与审查不同上下文），高风险经对抗式红队。

### DOD-P1（规则数据）
- [ ] `rules/*.yaml`、`flow.yaml` 通过 `schemas/*.json` 校验（CI 强制）。
- [ ] 每条默认规则必带来源；低置信进 `draft`，不进默认集。
- [ ] 涉及官方后台提交/认证/备案/类目/隐私/域名/发布的规则 `manual_required: true`。
- [ ] 预检规则声明 `scanner`，动态命中用 `manual_only` + `dynamic_note`，不以 LLM 猜测冒充。
- [ ] `flow.yaml` 通过**图 linter**：指向存在、无环、唯一入口、唯一终点（`release` 为唯一 `next: null`）。

### DOD-P2（代码）
- [ ] 单元/接口/集成/冒烟测试通过；关键路径有 E2E。
- [ ] 预检默认 local-only；脱敏与忽略清单生效（见 `SECURITY.md`）。
- [ ] CLI 运行时依赖最小化:**"优先"= 允许有充分理由且过安全审计的最小解析依赖**(当前 prod 依赖 `js-yaml`→`argparse`,引入理由已记入 §2.1 技术债台账);**对外措辞不得宣称"零依赖",除非 `npm ls --omit=dev` 为空**(见 docs/10 FX-01)。新增依赖须说明理由并过安全审计。
- [ ] 性能基线达标（见 §4 性能门禁）。
- [ ] 发布 tag 必须是 `v<package.version>`，且 `package.json`、`manifest.json`、`package-lock.json.version` 与 `package-lock.json.packages[""].version` 完全一致。
- [ ] release workflow 的 lint 与版本一致性校验必须先于 npm / MCPB 两条打包路径，失败不得忽略。

## 2. 代码质量门禁（按阶段解锁）

| 维度 | 工具/方法 | 阈值（建议） | 阶段 |
|---|---|---|---|

### 2.2 当前扫描资源边界

- 单个文件超过 **5 MiB** 时跳过并计入 `skippedLargeFiles`，报告必须提示存在未覆盖内容。
- 一次扫描最多处理 **20,000 个实际遇到的目录项（Dirent）**；目录、被忽略文件和不可扫描扩展名都消耗同一递归预算，不能借“可扫描文件数不增长”绕过上限。
- 符号链接 / junction 不跟随，避免把项目外代码带入报告或形成遍历环。预算耗尽时返回 `truncated: true`，`check` 必须提示用户核对目录或拆分子目录重跑。
- 当前 walker 使用 `readdirSync`，仍会一次加载正在读取的单个目录；因此 20,000 项是**总遍历工作预算，不是单目录硬内存上限**。若需硬内存保证，必须另立流式遍历方案与基准后再宣称。

### 2.3 MCP 请求与错误契约

| 情形 | 响应契约 |
|---|---|
| 无效 JSON-RPC 请求信封 | `-32600` |
| 未知方法 | `-32601` |
| 未知工具、缺少必填参数、参数类型或枚举非法 | `-32602` |
| 真通知（不存在 `id` 字段） | 无响应 |
| 显式 `id: null` 的合法请求 | 正常响应并回显 `id: null` |
| 参数合法但工具执行失败 | `result.isError: true`，不是协议错误 |

该矩阵由 `tests/mcp.test.mjs` 锁定。当前工具 schema 对已声明的必填、类型、最小长度和枚举做校验，同时接受未知扩展字段；改变通知或 `id: null` 语义属于协议契约变更。

### 2.4 发布身份门禁

`npm run release:check` 以一个可测试的契约核对 tag 与四个仓库版本字段；`.github/workflows/release.yml` 在 `npm pack` 和 `npm run build:mcpb` 前依次运行 lint 与版本校验。2026-07-10 的核心强化阶段只在本地验证了正确/错误 tag、workflow 结构、`npm pack --dry-run` 与无联网 MCPB smoke；后续真实 PR/main CI 及 `v0.2.0-rc.3` tag、联网 pack、Draft Release 资产的当前证据与恢复入口统一记录在 `STRENGTHENING_PLAN.md`（`v0.2.0-rc.2` 的同类证据因校验和清单路径缺陷已被撤回，见该文件 §D）。不得用本节的设计契约替代实际 run、ref 与资产核对——**校验和的验收必须以下载者身份实测 `sha256sum -c`，CI 内生成成功不构成证据**。

## 3. 缺陷修复清单与分级策略

每轮把缺陷登记为修复清单，**统一分级处理**，修复后必须**回归验证**：

| 处理方式 | 触发条件 | 时限 | 回归要求 |
|---|---|---|---|
| **热修复** | 阻断交付准入（DOD 不过）、对外口径越界、schema 与示例自相矛盾、密钥泄露风险 | 本轮内 | 必须复跑相关门禁，留证据 |
| **延期修复** | 不阻断当前阶段、但二期前必须解决（如缺 issue 模板、缺 CI） | 标注解锁阶段 | 进入对应阶段时复检 |
| **不予修复** | 设计取舍/误报/超范围（如多端扩张诉求） | 永久 | 记录理由，避免反复提起 |

> 修复台账见 [`docs/10`](10-quality-inspection-and-slice-plan.md) §2（本轮 FX-01…FX-18 + 1 误报，含分级与回归点）；后续每轮的修复与回归证据追加到对应轮次的产出文档。

## 5. Dogfood 协议（交互与体验）

以**真实目标用户**视角验证，而非作者视角：

- **导航 Dogfood**（来自 `docs/04` Go/No-Go）：找 ≥5 个零基础/个体开发者读 `guide` 输出，≥3 人能**自述下一步该做什么**，否则导航文案不过关。
- **文档 Dogfood**（P0 现在可做）：以"刚用 AI 写完代码、零上线经验"的人读 `README`，记录每一处"看不懂/会误操作/找不到下一步"的摩擦点，回灌为改进项。
- **Agent Dogfood**（P2）：让 Claude Code / Codex 实际调用 CLI/MCP，检查衔接是否顺、输出是否可被 Agent 正确解释。

## 6. 分维度优化（每阶段复盘四问）

每轮结束按四个维度各回答一句"本阶段最大短板 + 一个可落地动作"：

- **质量**：哪条结论来源最弱/最可能腐烂？→ 加来源或降级 `draft`。
- **效率**：哪步靠人工重复？→ 能否脚本化（如链接体检、计数核对、schema 校验）。
- **稳定性**：哪条规则/分支最易随政策失效？→ 加 `last_verified` 监控与告警。
- **可维护性**：哪处是多事实源/重复？→ 收敛到单一权威源 + 引用。
