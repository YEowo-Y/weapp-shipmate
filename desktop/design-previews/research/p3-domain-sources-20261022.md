## 直接结论

可以复用现有八阶段及 63 条规则，但必须把“本机发现”“用户确认”“官方办理结果”分开。注册、主体核验、发布三个阶段目前没有规则条目，应显示细化要求尚未覆盖，不能通过空列表自动判定完成。已有阶段规则计数为 category 8、domain 4、filing 4、privacy 23、review 24；rules/ 中不存在 registration.yaml、certification.yaml、publish.yaml。

本轮找到可补充注册和发布的微信官方接入指南，以及可替换旧社区引用的认证专页。备案地址已经迁移，类目页比本地归档更新；不能仅刷新 `last_verified` 就把旧数据称作最新。新增规则必须另行归档正文、建立正反例、执行来源及规则门禁。

## 现有类目规则的具体复核

`corpus/source-snapshots/index.json` 中 material、reject、旧 record_guidelines 的归档日期均为 2026-07-17，不能代替今日在线材料。对 categories.yaml 的 8 条 `source_quote` 做 HTML 转文本后的精确包含检查：

- medical、payment、personal-subject-scope、news、live、law 六条引文仍存在。只证明引用片段存在，不证明整个启发式映射或文案已完整核验。
- finance 引文未精确命中，但银行/信托行仍列金融许可证与金融机构许可证二选一，主要是列表排版和措辞差异。需更新归档并按实际文本维护引文，不能仅靠字符串失败断言业务规则失效。
- education 引文未精确命中；当前表有课程销售平台、在线视频课程等更具体条目。课程销售平台的适用范围明确涉及多家机构，不能把“有课程/付费”直接推成“多商户课程销售平台”。需区分机构自营、聚合多机构、纯信息展示及音视频授课后再核对对应行。

特别注意：非个人类目表和个人类目表都可能出现相似词。先前截取非个人美容行不能证明 personal-subject-scope 旧引文消失；本轮全页检查已确认旧个人引文仍存在。关键词首次出现位置不足以验证主体范围。

## 可供执行者使用的最小事实与确认语义

以下是基于官方办理边界和 P3 验收条件的建议，不是官方 API 或必须采用的新数据协议。

| 信息 | 最小内容 | 确认方式 |
|---|---|---|
| 项目事实 | 主体、实际业务简述、是否有交易/支付、个人信息与服务器域名相关情况 | 用户明确填写；未知保留 unknown，不能由空字符串推为 false。扫描发现可作为建议，不能偷偷覆盖。 |
| 阶段确认 | projectId、stageId、确认时间、依据的项目事实修订及规则版本 | 用户在本机确认；显示“我已在官方后台确认”，允许撤销；不是平台回执。 |
| 本机证据 | artifactId/runId、执行时间、扫描范围、完整性、工具和规则版本 | 来自真实执行且契约校验后的结果；只能说已检出/本次未检出。 |
| 来源 | official_url、原 last_verified、可用性、规则/归档版本 | 在线打不开要显示未复核；不自动刷新核验日期。 |
| 类目候选 | 主体适用范围、用户业务描述、命中规则、材料提示、来源 | 用户到官方后台选择；候选不是已获准类目。 |

状态解释必须可区分：

1. **未知/待确认**：尚无人工记录或有效证据。
2. **人工已确认**：用户对指定项目、事实版本和规则版本作的确认，不等于联网核验。
3. **本机检查结果**：成功执行不等于合规，警告和检查范围仍展示。
4. **不适用**：有明确适用条件和充分事实；无细化规则、没有命中、没有发现文件都不是不适用。
5. **待重检/待重新确认**：主体/业务事实、相关规则或扫描边界变化后保留原记录并显式失效，不能删除审计历史。

注册、备案、审核与发布的完成状态均须人工确认。审核通过不能自动把 release 标完成。不能把流程中 certification 节点解释成所有主体必须付费微信认证；“主体核验”与“微信认证”是需要分开的概念。

## 可补规则候选及门禁

在本轮授权范围内不写规则；交给规则执行者的最小候选是：注册资料与激活、按官方后台选择主体验证方式、审核通过后正式发布。这些候选可由 introduction/ 与 renzheng.html 支撑，但必须按 `docs/06-quality-and-acceptance.md` 和本次 P3 计划补齐来源归档、日期、适用范围、正反例及独立评审。

- 新增默认规则不能只引用搜索摘要；没有完整材料证据时保留“尚未覆盖”，而不是编造要求。
- 依照 docs/06，涉及后台注册、认证、备案、类目、隐私、域名、发布的规则必须 `manual_required: true`。
- 备案旧地址可迁移到已找到的新官方地址；先归档并复核引用，历史报告版本不变。
- 来源页本身有可能存在陈旧条款。接入指南写个人暂不支持微信认证；认证专页也未列个人主体。未登录当前后台验证，不据此新增“个人永远不允许认证”的绝对禁令，更不能把个人主体标为无法上线。
- 当前 flow 的 privacy 条件使用敏感信息标志；不宜将“未发现敏感 API”扩展为“不处理任何个人信息”。没有完整事实时仍显示待确认，而不是泛化隐私豁免。

## 未覆盖与版本限制

本轮没有完成全部类目表逐行建模、全部法规的法律适用分析、地区备案差异、最新费用/时限/配额、个人认证产品变化、官方后台实机步骤截图，也没有新增规则语料或替换归档。未开展外部联系或五人用户验证。文件中的字段建议、比较/失效逻辑属于交接建议；实施方案与最终验收由主任务负责。

本研究只改本文，无产品构建或功能测试主张。现有质量门建议至少包括规则 Schema/图校验、source_quote 归档校验、正反例与主流程测试；精确命中仅证明文字对应，不能替代人工阅读适用范围。

## 可复用结论

先把八阶段显示成可解释的真实项目状态：缺来源则说明覆盖缺口，官方事项人工确认，自动报告保留扫描范围和版本。优先修复备案来源链接与教育类目泛化风险；注册和发布采用新找到的一手来源补齐后再进入默认规则。保持原组件、持久层和规则内核，本研究没有提出新增依赖。
